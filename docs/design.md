# 设计：账本、生命周期与提示词

这份文档回答**为什么**：账本为什么是文件而不是数据库、传递路径为什么是权威、修正与结案为什么长这样、提示词为什么分两段。动机、取舍与被否掉的替代方案都在这里；只想把插件用起来，读 [README](../README.md) 就够了。

## 为什么需要它

DSH 原本的代理间通信是**相邻 Agent 的 steer 投递**（`ctx.subagents.sendMessage`），它明确承认这些缺口：

- 只能投给**直接子代理**或**直接父代理**，兄弟、祖辈、无关同伴一律 `UNAUTHORIZED`；
- **没有持久 mailbox**：父代理不在线时消息被拒绝，而不是"先接受、后送达"；
- **没有抄送、没有优先级、没有回执、没有线程、更没有传递路径记录**（`AgentMessageSource` 只带一个 `senderSessionId`）。

本插件补上的是最后那一块地基。它不新造会话事件类型（那会让会话日志在重载时不可读，见下），而是复用 harness 已有的白名单词汇与公开 API。

## 核心设计

**汇报是两层结构。**

- **front matter 是缩略**：主题、收发、抄送、共写者、跳数、最后跳。它是唯一进入模型上下文的部分，因此长期协作的上下文开销是有界的。
- **正文留在账本里**，由 `report_read` 按需打开（超长时只返回头部与文件定位，模型用 `read` 分页取余下部分）。

**传递路径是权威的。** 每次操作都追加一跳（append-only JSONL），因此：

- `to` / `cc` / `authors` / `hops` / `last` 都是**从跳流派生**的缓存，任何下一条跳都会重新校正它——账本不可能显示历史里没有的收件人；
- **待投递集合也由跳流派生**：被投递过（`sent`/`cc`/`forwarded`/`copied`）且其后还没有新的到达（`delivered`）的收件人即为待投递——**一次到达只销掉它之前的那次投递**，之后再次主送会重新排队。**唤醒策略按窗口**：窗口内只要还有一次未答复的主送就 `steer` 唤醒，只有纯抄送时才 `inject`。**审计轨迹本身就是那个缺失的持久 mailbox**，所以它天然跨重启存活，且不可能与历史不一致。

**投递走公开的 Agent 入口。** 模型工具受"精确相邻"约束，但 `Agent.steer/inject` 只接收一条消息、不做授权检查，而任何活 Agent 都可由 `ctx.agents.get(id)` 取到。因此：

- 主送（`to`）用 `steer`——空闲目标会因此开启一个回合；
- 抄送（`cc`）用 `inject`——进入上下文但不唤醒任何人；
- **非驻留收件人不会被拒绝**，而是留在待投递集合里，等 `agent/created` 事件到来时自动送达；插件加载/重载时还会对当时已驻留的会话补投一次——这些会话不会再收到 `agent/created`，否则那份交接要一直等到下次 resume。

## 账本布局

根目录 `$DSH_HOME/report-ledger/`（可用 `DSH_REPORT_LEDGER_ROOT` 显式覆盖，便于部署迁移与隔离测试）：

```
reports/R-0001.md            front matter 缩略 + 正文
reports/R-0001.route.jsonl   append-only 传递路径，一行一跳
```

写文档走 temp + rename（Windows 的共享冲突做短重试，失败会清掉 temp）；进程被强杀可能留下 `R-0001.md.<hex>.tmp`，目录扫描会忽略它。

选择文件而非私有数据库，是因为账本是一段协作的长期记忆：它必须可被人直接检查、手工修正（写错主题、补一句 hop 说明都不需要迁移；Windows 的 CRLF 与 BOM 也能读），而 front matter 让"只读缩略"不必打开正文。

front matter 里唯一和工作区有关的字段是**可选的** `worktree` 块（`path` / `branch` / `head` / `repo` / `allocated`）；它缺席是常态，老账本不需要任何迁移。跳动作词表里对应三个：`leased`、`released`、`reclaimed`——一个被 `parseHop` 丢弃的动作就是一段无声消失的审计，所以词表是**单一来源**（类型与运行期校验都从同一个常量派生，加动作时漏改一处会被编译器逼出来）。

### 读路径：只读缩略，且同一份文件只读一次

读取是账本最高频的操作——每次工具调用、浏览器每 10 秒的轮询、每次投递扫描都从缩略列表开始。实测（本机 Windows + 实时防护）一次 open/read/close 约 **1.3 ms 串行、0.34 ms 并发，且与字节数几乎无关**：200 份汇报，正文从 0 到 32 KiB（账本 100 倍），`listReports` 都是 300 ms 上下。所以该优化的不是"少读字节"，而是**少开文件、少读一遍、别按会话数翻倍**：

- **缩略只读文件头。** 列表打开每份文档只读前 16 KiB（`DIGEST_HEAD_BYTES`），读到闭合围栏就停，正文永不进内存。这是预算而不是假设：front matter 超过它、或文档正好在围栏处结束且没有结尾换行（那是"前缀"还是"整篇"在读取端无法区分），都会退回整篇读取——慢，但记录不会因此消失。
- **同一份文件一次变更只读一次。** 缩略与跳流按文件的 `mtime`/`ctime`/大小签名缓存；本进程的写入直接刷新缓存条目，跳流追加与正文追加作废对应条目。别的进程写入靠签名就能看见——**缓存是派生状态，不是第二份权威**，因此既没有要调的 TTL，也没有"短到可以接受"的不一致窗口。
- **并发有上限。** 一次列表最多 32 个文件同时在读（`READ_CONCURRENCY`）：200 份汇报的冷列表 300 → ~130 ms，热列表（只 stat）~11 ms。
- **投递扫描只走一趟账本。** 补投原本是"每个驻留会话扫一遍全库"：20 会话 × 200 汇报 = 8000 次文件读，实测 21–31 秒，而它恰好发生在插件加载后与每次 `agent/created` 之后——磁盘被占满的那段时间里，所有读取都跟着慢。现在 `flushSessions` 读一遍账本、一次回答所有等待中的会话（同样场景：冷 ~310 ms、热 ~32 ms）。语义一条没让步：待投仍从跳流派生、每份汇报仍在自己的锁里重读跳流后才投、单份失败仍不影响其他。
- **正文不缓存。** `report_read` 与详情面板拿到的始终是文件当前内容；正文多大，都只影响它自己那次读取，不影响列表。

⚠️ 边界：一个文件在同一时间戳刻度内被改成**相同大小**（只可能来自外部进程绕过本插件写盘）时，签名看不出变化。这一格是刻意留的——把每条读取都改成整篇读取来堵它，代价正是上面那张表。


## 修正：记录，而不是抹掉

一个 agent 写错了主题时，原本只有两个坏选择：重开一份新汇报（丢掉原有传递路径与收件人），或者让错误留着。而人手改文件又能改——**这个不对称是实现漏洞，不是设计取舍**。

难点在于：账本的价值来自**历史只增不改**；如果 agent 能静默重写记录，账本就不再可信。所以 `report_amend` 的规则是**修正必须被记录**：

| 对象 | 语义 | 理由 |
|---|---|---|
| 缩略字段（`subject` / `task` / `artifacts`） | **替换**；`subject`/`task` 在跳里逐字记录改前改后，`artifacts` 记录数量变化（如 `2 -> 3`） | 它们是**当前状态**，不是历史；而"从什么改成了什么"正是审计要的 |
| 正文 | 默认**追加**一段 `### amendment` | 正文记录的是**人说过的话**，改写别人的话就不是记录了 |
| 正文（`replace_body: true`） | 真替换，且跳里注明"body replaced" | 有时确实需要重写；那就**让后人知道被重写过、被谁重写**，而不是被误导 |

**收件人与共写者永远不能在这里改**——它们由跳流派生，唯一的修改途径就是再追加一跳。`task` 传空串可以**清除**标签（避免出现"空标签"与"无标签"两种含义）。

修正属于活动，所以**给已结案的汇报做修正会自动重开它**并记录 `reopened`。

实测效果：一个写了错别字的主题被改正后，落盘是

```
front matter:  subject: "the corrected title"          ← 当前真相
传递路径:      amended  # subject "teh wrong speling…" -> "the corrected title"   ← 历史
```

## 汇报的生命周期

三个状态：`open` → `acked` → `closed`。

| 动作 | 谁能做 | 效果 |
|---|---|---|
| `report_ack` | 任何收件人（`to`/`cc`/共写者/发起者）；非收件人会被拒绝并列出可回执的人 | 记一跳；`open` → `acked`。**回执 = "我收到了"** |
| `report_close` | **仅发起者或共写者** | 记一跳；→ `closed`。**结案 = "这件事结束了"** |
| 贡献 / 主送 / 抄送 / 转呈 | 任何有权限者 | **自动重开**：先记 `reopened` 跳，`closed` → `open`，随后才落下活动本身那一跳 |

两个刻意的设计决定：

**1. 结案是拥有者的事，不是读者的事。** 只有发起者或共写者能关闭；被拒绝时错误信息会**报出该找谁关**（列出作者），而不是只说一句"不行"——这样代理知道下一步该做什么。`from` 与 `authors` 都算拥有者，因为手改过的账本可能缺对应跳，而拒绝明显的主人会让汇报永远悬着。

**2. `closed` 是状态，不是锁。** 如果有人在关闭后又贡献／主送／抄送／转呈，那这件事显然又活了，于是自动重开并记录 `reopened` 跳。否则一份被过早关闭的汇报会**静默吞掉后续工作**——对一份以可追溯为全部意义的账本来说，这是最糟的失败模式。

所以**不需要单独的"重开"工具：活动本身就是重开**。回执与结案也是刻意不合并的两件事：回执表示"我收到了"，事情仍在推进；结案表示"这件事结束了"。对已关闭的汇报回执只记跳，**既不重开也不降级为 acked**。

状态机每一次转换都落在 append-only 路径里：

```
authored → closed(note) → reopened → contributed
```

未来读者看到的是过程，而不只是当前终态。


## 退役与交接：一个会话名下的一切怎么处理

账本里的"代理"是**会话 id**：汇报的发起者与共写者、检出的占用、待送达的收件人、workspace 的归属，全部按会话 id 记账。预设只是"还能不能再开一个这样的人"的模板。所以代理退场不是删一行配置，而是一次**声明式的资产转移**。

### 四类资产，可转移性不同

| 资产 | 能否转移 | 机制 | 缺口 |
|---|---|---|---|
| 未结汇报的处置权 | 能 | 继任者 `report_contribute` → 成为共写者 → 可 `close` / `amend` / `lease` | 无 |
| 未结汇报的"债"（待送达） | 只能换人，不能撤销 | `report_transfer` 记 `transferred` 跳 | 依赖本功能（见下） |
| 检出占用（分支锁） | 不是转移，是认领 | 原持有者 `report_release`，继任者 `report_lease` | 原持有者消失时，占用会一直计入 `maxActive` |
| 会话本体 | **不可** | 只有引用（`artifacts`）与转呈（`report_forward`） | 无，也不该有 |

### `transferred`：一条必须存在的跳

待送达是**从跳流派生**的（`pendingTargets`）：有人被投递过、但没有 `delivered`，就欠着。这套推导没有任何"撤销"操作，于是收件方永不回来时，义务会永远挂着。`transferred` 是唯一的正解——它**不是**送达：没有人收到东西，只是换了人欠。

```
authored → sent → transferred(from=旧收件人, to=新收件人) → delivered(to=新收件人)
```

权限刻意窄：**拥有者**（发起者/共写者）可以改自己汇报的派发；**当前欠着这笔投递的会话**可以把自己的义务交出去（它是唯一无法履行的一方）；其他人不行——没人可以抢在一笔已送达的投递前面改道。唤醒策略随义务一起走：本该唤醒的仍然唤醒，静默抄送的仍静默。

### `report_handover`：把交接变成一个动作

它先枚举（`assetsOf`：摘要定候选、跳流定状态）：该会话仍开着且归它的汇报、其中仍占着检出的、仍欠它却没送达的。然后按调用者分两种模式：

- **调用者就是 `source`（退役模式）**：可以结案 `close` 里点名的汇报、把每一笔未清的投递转给继任者、交还它占着的检出（`release`，磁盘原样保留）。
- **调用者是继任者（接管模式）**：对 `source` 名下每一份未结汇报 `report_contribute`——**共写是这里获得权限的唯一方式，而且它总是一条被记录的跳**；然后搬它能搬的投递。搬不动的（它既不是拥有者、也不是欠着的那个会话）如实报出，不绕过。

无论哪种模式，它都会落下**一份 `task: handover` 汇报**，正文列出"发现了什么、做了什么、留给继任者什么"。于是退役是账本里的一个事实，而不是一段缺席。

两个刻意的约束：**检出永不自动删除**（`release` 只结束占用，目录留在磁盘上）；**搬不动就报错**，绝不把部分成功渲染成完成。

### 在开发者模式里

名单条目的 `retired: true` 是这套机制的入口：该条目不再注册为可选预设（开不了新会话），但**仍留在提示词路由表里**，于是正在跑的会话不会在某次装配时突然失去职责说明，而是收到一段收尾指令，让它用 `report_handover` 结束自己的事。`dev_agents_reload` 的输出会单独列出 `retired:` 一行。

> 删掉条目**不是**退役：那会让存活会话的提示词当场变空，它自己还不知道。


## 提示词：协议与伙伴契约

插件注入**两段** `systemPrompt.section`，这个拆分是有意的：

| 段 | 名字 / 顺序 | 求值方式 | 理由 |
|---|---|---|---|
| 协议 | `plugin:report-ledger` / 200 | 静态字符串 | 对所有 agent **逐字节相同**，因此是各 scope 里稳定的提示词前缀（KV cache 友好） |
| 伙伴契约 | `plugin:report-ledger:partnership` / 201 | 按 assembly 求值的函数 | 契约要对两种读者说不同的话 |

**协议段**说明账本是什么、各工具做什么（`report_*` 十三个，工作区功能关闭时不暴露 `report_lease`；另有 `peer_list` / `peer_start`），以及会改变行为的约定：收件方不在线不是错误（投递会被持有）；路径由账本自动记录，但每一步都必须经工具完成；工作区若启用，独立的是哪些、共享的是哪些；**会话或网络中断后先对账再继续**——用 `report_list` / `peer_list` 找到最后落下的跳、谁已交付、谁还在线，以汇报正文/任务标签/传递路径为检查点，不从头重做，重试前先确认动作是否已经落地。协议段为了保持前缀逐字节相同而**不按部署改写**，工作区的"有/没有"这一部署差异写在下面的伙伴契约段里。

**伙伴契约段**分两种读者：

- **对所有 agent**：明确否定"工具"框架——*其他代理不是「做完一项任务就可以终止的工具」，而是长期相处的同伴*；一次任务的结束是这段关系的逗号而不是句号；交接用汇报而非口信；收到汇报要回执；兄弟代理之间也可以互相抄送。
- **仅对被委派的子代理**：你的会话是持久的、不是一次性函数调用；**主动汇报，不要默默结束**；**你的父会话 id 是 X，可直接主送到它**；权限范围启动即固定，需要越界时把限制写进汇报而不是反复重试。

**角色判定是同步且精确的**，来自 `Session.header`（`origin === 'subagent'` 或 `delegationDepth > 0`）——持久、首次组装时就在，无需查询、无需缓存、无异步竞态。子代理的父会话 id 也由此取得并**直接内联进提示词**，因为不给出这个地址，"向上汇报"就只是一句无法执行的口号。
