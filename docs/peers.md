# 同伴：代理自主开启会话

`peer_start` 开出来的是**独立的根会话**，不是子代理。本文写它与子代理的区别、创建时必须继承什么、它落在哪个工作区分组、以及这条路上踩过的每一个坑。工具层面的用法在 [README](../README.md) 里。

三个工具：

| 工具 | 作用 |
|---|---|
| `peer_list` | 列出你能对话的代理及其与你的关系（上级 / 下属 / 兄弟 / 你开启的同伴 / 账本里有往来的联系人），并标注谁此刻在线 |
| `peer_start` | 开启一个**独立同伴会话**，把任务作为一份**汇报**交给它，并报出它第一个回合的**观测结果**（在跑 / 已结束 / 失败）；`report` 可把一份**已有汇报**直接交给它（不新建作业单，并且在该汇报的检出里开工），`parent` 让新作业单挂到某份汇报下 |
| `peer_wake` | 把一个**你开启的、已离开的**同伴叫回来：宿主重新加载会话，账本随即投递还欠着的交接，并观测它的回合。只有开启者能唤，不占名额，账本没有欠它投递时直接拒绝 |

## 同伴是独立根会话，不是下属

这是本阶段最重要的设计判断。`peer_start` 创建的会话**没有 `parentSession`、没有 `origin`、`delegationDepth` 为 0**——它是一个根会话。这样它才配得上"同伴"：不占用任何委派深度预算、出现在工作区会话列表里（见下节：这一步需要显式挂账，不会自己发生）、**并且比开启它的那一轮活得更久**。

"独立"说的是**生命周期**，不是**能力**。新生的根会话自己既没有组合（composition）也没有模型路由，缺哪一样它的第一个回合都会当场死掉：没有组合就只看得见空的全局层（没有预设工具、没有预设提示词段）；没有模型路由则在提示词组装时解析不出 `{{model}}`——回合在第 1 步就以 `error` 结束，**一个工具都没调到**。所以这两样必须**从开启者身上取**：

- **组合**：`agentPresets.composeFrom()` 把同伴绑到开启者**正在跑的那一代**（不是按 id 重新解析——预设文件自开启者启动后被改过或删掉，都不会让同伴跑在另一个世界里）；部署没有名册时什么也不绑，也不报错，与委派子代理同一套语义。
- **路由**：provider / model / reasoning effort 继承开启者的会话请求头（请求头是请求期选择之后的真实路由），未发过请求时回落到它的创建选项，再回落到部署默认模型；**三者都没有就拒绝创建**，而不是造一个注定失败的会话。
- **预设身份**：绑到的预设 id 写进会话头，否则冷读同伴的日志会按部署默认重建出一个它从没跑过的组合。
- **权限**：开启者**当时的有效**沙箱模式、审批策略与预设身份一起继承，以 `source: 'delegation'` 写进**同伴自己的日志**（与 `dsh-subagent` 的委派子代理用同一个标记、同一个创建窗口）。这一条最容易漏，因为漏了**不报错**：同伴只是被钉在部署默认预设上，于是从"完全权限"会话里开出来的同伴，反过来要你批准一件开启者本来就能做的事；从"仅可查看"会话里开出来的同伴，比开启者权限更大。`custom`（匹配不上任何预设的派生状态）不作为身份复制，但两个旋钮照旧继承，同伴因此落在同一个自定义状态上；之后在同伴会话里再切一次，只是日志上更晚的一条事件，照样生效。宿主若没把未发布的会话交给 `setup()`，捕获失败会在部署日志里留一条警告，而不是静默退化。

代价是血缘无法表达这段关系（`parentSession` 是空的），所以**名册日志**（`$DSH_HOME/report-ledger/peers.jsonl`，append-only）记录它：谁开启了谁、何时、什么名字、继承的工作目录。这条记录同时是**授权凭证**。

## `delivered` 不等于"有人在干活"

投递只证明摘要到达了一个**常驻**代理；它证明不了回合开没开。而一个在第 1 步就死掉的回合，和一个正埋头干活的同伴，在账本里长得**一模一样**：同一跳 `delivered`、同一行 `live`。所以 `peer_start` 交完任务后会观测一个有界窗口（默认 1500 ms，`DEFAULT_RECEIPT_MS`），如实报出四种之一：

| 观测 | 含义 |
|---|---|
| `running` | 回合开着，窗口关闭时还开着 |
| `settled` | 窗口内回合跑了并且结束了（附结束原因） |
| `failed` | 窗口内回合以 `error` 结束（附错误原文）——这正是过去完全看不见的那一类 |
| `unstarted` | 收件箱里有活，但从未开过回合 |

这是一次**观测**而不是状态查询：它把"交接完成"与"有人在干"分开，代价是 `peer_start` 多等一个窗口。

## 同伴进哪个工作区分组

"出现在工作区会话列表里"这句话需要补一句：**它不会自己发生**。

侧边栏的分组只读工作区的账目（`workspace.json` 里每个工作区的 `sessionIds`），而这个账目只有两个来源：

1. **一次性历史对账**——注册表首次初始化时（`initialized` 标志为 false 的那一次）把已有会话按规范路径分桶补录。**之后永不重跑**：非首次启动时只做「按 header 索引重建」，而那个索引的用途是**剔除**路径对不上的条目，不是补录；
2. **创建时显式挂账**——调用方在 create 请求里点名 workspaceId。GUI 里从某个工作区新建会话走的就是这条；**Fork** 也走（继承源会话的工作区）。

`peer_start` 两条都够不着：`ctx.agents.create()` 的创建元数据只有 `cwd` 和 `agentPreset`，**没有工作区身份**；而对账在同伴存在之前早就跑完了。于是出现一个很别扭的状态——**同伴的工作目录与某个已注册工作区逐字相等，它的 id 却不在那个工作区的账目里**，浏览器按账目分组，就把它永远放在「未分组」。

修法是宿主侧一个**可选钩子**（`PeerHost.attachToWorkspace`）：同伴**创建之后**（注册表要校验会话头里的 `cwd`，而头在会话存在之前不存在），宿主解析同目录的工作区并把新会话挂进去。三个设计要点：

- **按规范真实路径匹配**，不做字符串比较。注册表校验的是 `realpath` 归一化后的路径，用字符串比较会在大小写、分隔符、符号链接、8.3 短名上产生"要么挂错、要么被注册表拒绝"的分歧。所以宿主用的是注册表自己的 `resolveByPath()`。
- **可选依赖，不是硬依赖**。headless profile 没有工作区注册表（没有侧边栏可分组），硬依赖会让插件在那里永远等待。钩子缺失时报告"这个部署没有分组"，而不是失败。
- **三种结果，"只有一种是缺陷"**：`registered`（已挂账，报出工作区标题）、`no-workspace`（没有注册表，**或**该目录确实不属于任何工作区——同伴在自己的临时检出里就是这种，合法）、`failed`（尝试了并抛错）。`peer_start` 只对第三种打警告，因为对合法情形也警告，会让调用者学会忽略那一行——而那一行正是本机制存在的理由。注册失败**绝不**让创建失败：一个存在但归错桶的同伴仍是能用的同伴，被拒绝创建的同伴什么都不是。

这条路径正是被真实数据打出来的：本机 166 个会话里有 12 个根会话长期停在「未分组」，其中一个目录（`D:\Projects\dsh`）根本没有任何工作区记录。

## 这一段的验证分两层

`pnpm test` 里跑的是**确定性**检查（`scripts/roster-check.ts` 管服务侧、`scripts/workspace-check.ts` 管宿主适配侧）。它们用的是假注册表，因此证明不了「真实注册表会不会接受这次挂账」——而答案恰恰在注册表自己的校验规则里：`attachSession` 会读会话头、把 `cwd` 归一化，然后要求它**等于**工作区记录里的路径。用字符串比较代替归一化，注册会全部返回 `failed`、同伴照样停在未分组，而单元测试全绿。

所以还有一个**手动**探针（不进 `pnpm test`，因为它需要真实存储栈与真实会话日志）：

```powershell
# 在隔离的 DSH_HOME 上放一份真实 workspace.json 的拷贝（绝不写机器上那份），
# 再指向真实会话日志根，让真实 WorkspaceRegistry 跑一遍完整链路
New-Item -ItemType Directory -Force "$env:TEMP\dsh-probe-x\storages" | Out-Null
Copy-Item "$env:USERPROFILE\.dsh\storages\workspace.json" "$env:TEMP\dsh-probe-x\storages\"
$env:DSH_HOME = "$env:TEMP\dsh-probe-x"; $env:SESSIONS = "$env:USERPROFILE\.dsh\sessions"
node scripts/registry-attach-probe.ts 'D:\Projects\dsh-report-ledger' 'session-<真实会话 id>'
```

它挂载真实的 JSON 存储后端、真实 storage domain、真实 JSONL 持久化与真实注册表（离线显式跑一次服务的 init hook，因为这里没有 Loader），然后断言：注册表能看见拷贝里的 8 个工作区、非规范拼写（全大写 + 尾随分隔符）也解析到规范路径、插件自己的适配层能把一个**真实会话**挂进去、活体读回成员已生效、重复挂账幂等。5/5 通过，即证明这条链在生产包上成立。

## 关系分类，不是投递授权

DSH 的委派层拒绝非相邻通信，源码原话是"其他代理、祖先、teams、workflows、hosts 保持拒绝，**直到有一个显式的授权协议有生产消费者**"。本插件**不声称**自己是那个消费者：它画的是关系图，不是门禁。

**`report_send` / `report_cc` / `report_forward` 按设计接受任何会话 id**——正因为"通过账本联系对方"是建立接触的方式，把接触本身也设成门禁就形成了循环（先有鸡还是先有蛋）。所以本插件**没有投递前的权限校验**：血缘、同父兄弟、"我开启的会话"、账本里有往来，这些只决定 `peer_list` 里显示什么关系、怎么排序；`holdsChannelTo` 在投递路径上没有任何调用者。真实存在的闸门只有两条：**工具可见性**与 **`maxPeersPerAgent` 预算**。

创建会话是本插件唯一会**新增活代理**的能力（其余都只是记录），所以它的授权故事是叠加的：工具可见性（DSH 自己认定的唯一真实闸门）+ `maxPeersPerAgent` 预算 + **继承调用者自己的工作目录**（无法被指向无关目录树）+ 每次创建都在名册里留痕。预算是**本会话终身**额度（默认 8），不是并发额度：已经离开、或首轮就死掉的同伴**照样占名额**，名册日志就是计数；超限是明确的工具错误，错误信息会说明这一点并给出回收办法——**备份后**从 `$DSH_HOME/report-ledger/peers.jsonl` 删除已结束同伴的那几行（append-only JSONL，删行只影响计数与关系归类）。

## 创建与对话是分开的

`peer_start` 只负责创建与记录；**交任务由调用者用一份汇报完成**（工具层组合两者）。于是：任务天然进了账本、驻留的同伴被投递唤醒（非驻留的只挂账——要它回来用 `peer_wake`，见下节）、路径被记录，而同伴之后对同一份汇报的 `report_contribute` 就让它成为双向线程。这正是"用汇报做交互的关键"——S4 **没有**引入第二条轻量消息通道，因为那会产生一条不受审计的旁路，正好抵消 S1 的全部价值。

**两种交法，取决于那份汇报是否已经存在。** 默认是给同伴新开一份作业单（正文写"你是同伴、怎么回复、任务是什么"）。但如果调用者**已经**写好了一份线报告，再开一份只写着"请读那份报告"的作业单就是重复——`peer_start(report="R-0037")` 直接把那份报告交给同伴：**不新建任何汇报**，只记一跳 `sent`，而且**同伴在那个报告自己的检出里开工**（检出属于报告，不属于这次调用）。这正是"每条线占一个检出"该有的形状：`report_author(worktree:true)` 开线报告并拿到检出 → `peer_start(report=<那份报告>)` 让同伴进去。

一处刻意的边界：**同伴契约走跳的 note，不走正文**。正文是调用者的报告，往别人的报告里 `contribute` 会让调用者成为共写者（也就是拥有者，能改能关）；note 是每个收件人在 `report_read` 里都会读到的路径的一部分，够用而不越权。另：已结案的报告会被拒绝而不是静默重开——重开应该是有人贡献的结果，不该是派活时的副作用。想让新作业单挂进树里，用 `parent`（`report` 与 `parent` 同时给会被拒绝：已存在的报告不是新的树节点）。

## 唤醒：把"等它回来"变成可执行的动作

投递是 `steer` 给一个**活着的**代理，所以一个跑完回合、已经转为非驻留的同伴，在账本里是彻底够不着的：邮箱持久，恰恰因为它自己不做任何事。`peer_wake` 补的就是这半步——用 `ctx.agents.resume()` 把持久会话重新加载（组合与模型路由照旧从开启者继承，因为唤醒出来的是一个同样没有自己装配的根代理），随后插件原有的补投扫描把欠它的投递送进去，再观测一个有界窗口。

三条边界是设计的一部分：

- **只有开启者能唤**（名册里 `startedBy` 那一行）。唤醒比"发消息"更接近"创建"——回来的代理带着它自己日志里记录的那套权限继续跑——所以它跟随 `peer_start` 的授权故事，而不是 `report_send` 的开放式寻址；被拒绝时会点名该找谁。
- **不占同伴名额**。它加载的是已经存在、且早已占着名额的会话；若唤一次要花一个名额，"复用你手头那个同伴"就成了昂贵选项，正好和预算的目的相反。
- **只在账本还欠它投递时才有意义**。没有欠账还去加载一个同伴，会花掉它的上下文去读一个空收件箱，什么也证明不了——所以工具先问账本"还欠它什么"，答案为空就直接拒绝并说明改用 `report_send`。

加载失败必须出声：宿主的原话保留，同时明确"没有任何投递被送达、义务仍在它身上"，并指向 `report_transfer` / `report_handover`。否则失败看起来和"排队、等它回来"一模一样，而那正是这个能力要终结的误解。另外，**权限继承刻意不在唤醒时重做**：那套状态在创建时已写进同伴自己的日志，暖启动从那里恢复；每次唤醒都重新捕获开启者的当前状态，会覆盖同伴自己在会话里改过的开关。

## 一个必须记住的 API 陷阱

`AgentHandle.dispose()` 会"停止循环、注销代理、**并从 store 里移除该会话**"。所以对"必须比这一轮活得更久的同伴"**绝不能**持有或自动释放 handle——本插件创建后即丢弃 handle，同伴通过 `ctx.agents` 保持可寻址。自动 dispose 会删掉同伴的会话。

## 一处已知限制

在**一次性 headless 运行**里，开启的同伴不会真的执行任务：它不是子代理，因此不在运行器 drain 的范围内，父任务一结算进程就退出了。任务本身不丢——投递已作为 `agent/inbox/spliced` 进入同伴的会话日志，会话恢复时它就在历史里。在长期运行的 web profile 中同伴会正常处理收件箱（第一个回合的观测窗口在这种情况下最有用：它当场就能告诉你同伴是跑起来了还是死在第 1 步）。
